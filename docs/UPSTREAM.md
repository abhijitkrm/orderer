# UPSTREAM — issues found in matcher while building orderer

## 1. `OrderMap::remove` drops live keys (matcher-rust, matcher-cpp)

**Status: fixed upstream.** matcher-rust `71a35f4` (`src/ordermap.rs`,
plus `tests/regress.rs`) and matcher-cpp `1285f6c`
(`include/matcher/detail/internals.hpp`, plus `tests/regress.cpp`).
orderer-rust vendors matcher-rust `71a35f4` verbatim. Affected: matcher-rust
before `71a35f4` and matcher-cpp before `1285f6c`. matcher-java and
matcher-ts implement the algorithm correctly; matcher-go uses a built-in
map.

**Bug.** In the backward-shift deletion (Knuth 6.4, Algorithm R), when the
entry at `j` cannot move back into the hole (its home slot is in the
cyclic interval `(hole, j]`), the code still sets `hole = j`. The hole now
sits on a live entry, and a later shift overwrites that entry:

```rust
if !in_interval {
    /* move j → hole */ hole = j;
} else {
    hole = j;   // ← bug: an entry that cannot move must leave the hole where it is
}
```

The key silently disappears. A later `remove` of that key misses, so the
map's `len` drifts from the pool's live count. The order becomes
unreachable: cancels and replaces reject with `unknown_order_id`, and in
time level totals underflow. That shows up as a subtraction-overflow panic
in `cross()` in debug builds, and as corruption or hangs in release.

**Why the corpora never caught it.** It needs probe clusters with
deletions, which means a dense map: live orders near
`OrderMap::with_capacity(max_orders)`'s table size. matcher's vectors and
fuzz corpora use `max_orders` 4096 (8192 slots) with few concurrently live
orders.

**Reproducer.** `vectors/regress/001_dense_map_churn.cmd.jsonl`: 400
single-book commands, `max_orders` 32, 48 ids. Expected stream
`*.evt.jsonl`, generated by orderer-rust and confirmed identical with
matcher-java and matcher-ts. matcher-rust and matcher-cpp diverge at line
328: they reject a cancel of live order 4 as `unknown_order_id`.

**Fix** (both ports): in the can't-move branch, do nothing; only the scan
advances. orderer-rust's version, plus a model-based churn test:

```rust
let mut hole = i;
let mut j = i;
loop {
    j = (j + 1) & self.mask;
    if self.used[j] == 0 { return Some(val); }
    let home = (mix(self.keys[j]) as usize) & self.mask;
    let in_interval = if hole < j { home > hole && home <= j } else { home > hole || home <= j };
    if !in_interval {
        self.keys[hole] = self.keys[j];
        self.vals[hole] = self.vals[j];
        self.used[hole] = 1;
        self.used[j] = 0;
        hole = j;
    }
}
```

Remaining follow-up: add `001_dense_map_churn` to matcher's shared
`vectors/` (an `edge/` vector) so every port runs it through its golden
suite. Today the stream lives in matcher-rust's and matcher-cpp's own
regression tests.

## 2. matcher-cpp `Engine` built a whole book per command (performance)

**Status: fixed upstream** in matcher-cpp `5ddb7d2`. Found while porting
orderer-cpp.

`Engine::submit` and `submit_tagged` passed `OrderBook(default_cfg_)` as a
`try_emplace` argument. A function argument is evaluated on every call, so
each command constructed and discarded a complete book: pool reserve, a
2 × `max_orders` order map, and price ladders for both sides.
`submit_tagged` also built a `std::function` per call. Results were
unaffected; time was not. The fix looks up first, constructs only for a new
symbol, and takes the callback as a template parameter. A 200k-command,
8-symbol fuzz corpus through `matcherfuzz` went from 1.41 s to 0.63 s, with
byte-identical output. matcher-cpp's published benchmarks drive `OrderBook`
directly, so they were never affected.

## 3. matcher BENCH.md ops/s include per-op clock reads

matcher's protocol (`spec/matcher/BENCH.md` §2) times every command
individually. On Apple M1 the two clock reads cost about as much as a W4
command, so reported ops/s is about half of untimed throughput (W4: about
12M timed vs about 25M untimed for matcher-rust). That's fine for latency
percentiles, but misleading as a throughput headline. orderer's BENCH.md
1.1 reports both and gates on untimed. matcher could add an untimed column.

## 4. matcher-go `depth` allocated by the requested count (performance)

**Status: fixed upstream** in matcher-go `53b222a`, with a regression test
(`TestRestingOrdersAllocatesByLevels`). Found while porting orderer-go.

`OrderBook.RestingOrders` asks each price index for every level with
`depth(1 << 30)`, and both indexes preallocated `make([]levelDepth, 0, n)`:
a zeroed 16 GiB slice per side, per book, per snapshot. matcher-go's own
snapshots were only slow (the regression test took 145 s before the fix).
orderer-go's engines snapshot in parallel, and the OS killed the process.
The fix sizes the slice by the levels present. Snapshot output is unchanged.
